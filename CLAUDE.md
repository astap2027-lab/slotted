# Slotted

A gym planner for students who play sport. It fits gym sessions around school, sport and other commitments, tracks lifts and progress, estimates muscle recovery, and has an AI coach. Owner: Axel (a student in Sydney). Keep explanations to him short and plain.

## Rules that always apply
- **Upgrade, never rebuild.** Keep the current design (dark theme, lime accent, Archivo font), navigation, pages and every feature. Do not reset or discard saved data. Any change to stored data must read old data correctly (no destructive migrations).
- **Safety for teenage users:** no calorie targets, no supplement advice beyond "ask a GP or parent", refer pain to a physio or GP. Recovery and fatigue numbers are estimates, never medical measurements. Keep the safety rules in `js/coach.js`.
- **Strava data never goes to the AI coach.**
- **The coach never changes the plan by itself.** It proposes; the user accepts.
- All numbers come from app logic, not the AI. Charts show only recorded data. No decorative buttons or placeholder features.
- Logging must stay quick: pre-filled sets, one tap to tick.

## Stack
- Plain HTML, CSS and ES modules. No framework, no build step. Data is stored in the browser (`localStorage` key `slotted:v1`), with optional Google sign-in sync.
- Hosted on Cloudflare Pages from the GitHub repo `astap2027-lab/slotted`. Pushing to `main` deploys. Server code is Cloudflare Pages Functions in `functions/api/` (coach, auth, sync, Strava, account) with a D1 database (`schema.sql`).
- The coach secret is `ANTHROPIC_API_KEY` in the Pages project settings. The model is `claude-haiku-5-5` with API version `2026-10-21`. It thinks by default, so keep `max_tokens` generous; `functions/api/coach.js` retries without thinking if no text comes back.

## Commands
- `npm test` runs all tests (`node --test tests/*.test.mjs`). Keep them passing; add tests for new logic.
- `python3 -m http.server 8765` then open http://localhost:8765 to try the app locally (API features need the deployed site).
- `node tools/build-preview.mjs` builds `dist/slotted.html`, a single-file preview. It concatenates every module and strips imports and exports, so **top-level names must be unique across all files in `js/`**. New modules must be added to its file list in dependency order.
- When you add or rename a file in `js/`, add it to `SHELL` in `sw.js`. **Bump the `CACHE` version in `sw.js` and `APP_VERSION` in `js/app.js` together on every release** (`tests/release.test.mjs` checks they match; Settings shows "Slotted version N").

## Where things live
- `js/app.js`: every screen (Home, This week, My week, Routine, Workout mode, Progress, Coach, Settings, setup), routing, logging and sync.
- `js/scheduler.js`: week planning (free time, session placement, spacing, sport-day rules, time-of-day preference), splits, A/B weeks, streaks, suggested exercises (`MOVES`), custom routines.
- `js/exercises.js`: **the exercise library** (about 200 exercises), detailed muscles (`MUSCLE_INFO`, grouped by `MUSCLE_GROUPS`), tracking types, load types, search, alternatives, custom exercises and validation.
- `js/freshness.js`: muscle recovery estimate per detailed muscle (built on the original model), effort and intensity scaling.
- `js/progress.js`: per-exercise history and personal bests, type-aware (weight, reps, time, distance).
- `js/stats.js`: Home and Progress numbers (consistency, volume, records, finished workouts).
- `js/timetable.js`: which commitments apply each week, plain-words changes, validation and apply. `js/adjust.js`: fatigue-aware suggestions.
- `js/units.js`: kg/lb conversion, bar and plates. `js/tracking.js`: how each tracking type is logged, suggested, compared and written out.
- `js/workout.js`: rest timer lengths, plates, warm-ups, older swap logic. `js/readiness.js`: daily check-in. `js/coach.js`: coach instructions and client. `js/sync.js`: merging two devices. `js/store.js`: saving, defaults, backup.
- `styles.css`: the design system. `index.html`, `privacy.html`, `sw.js`, `manifest.webmanifest`.

## Data model (keep compatible)
- `state.history[weekKey]` holds `{ plan, done, skipDays, shortKeys, busy, checkins, swaps, skips, times }`. Week keys are Monday dates (`2026-11-02`).
- `state.log[weekKey][sessionKey][move]` is a list of sets `{ kg, reps, done }`. New fields `sec` and `m` are allowed. **Weights are stored in kg.** Older plank logs put seconds in `reps`; `secOf()` in `exercises.js` handles that.
- A `move` is either a built-in movement slot (`squat`, `horizontalPush`, and so on; its name depends on equipment via `moveName`) or `x_<slug>` made from an exercise name (`exerciseKey`). Never rename stored keys. Map them to library exercises with `exerciseForMove(move)` (the app sets the resolver with `setMoveResolver`).
- Custom exercises are planned to live in `state.customExercises` (ids start with `u_`). `sync.js` already merges them; `setCustomExercises()` loads them into the library.

## The current upgrade
The full brief is in `docs/upgrade-brief.md`. Axel chose:
1. **Muscle map:** keep the body map at group level. Tapping a group expands it into its individual muscles, each with its own freshness, recent exercises and dates.
2. **Effort:** one optional tap per exercise after it's done (Easy / Hard / To failure). Skipping it means "normal hard set".
3. **Delivery:** in stages, tested as each lands.

### Stage 1: exercise library and tracking (done)
- `js/exercises.js`: the library, detailed muscle mapping (primary 1, secondary 0.5, stabiliser 0.2), search, alternatives, custom exercise validation, `volumeOf`, `secOf`, `targetOf`.
- `js/units.js`: kg or lb. Weights are always stored in kg; `fromKg`/`toKg` convert for display and input. lb uses a 45 lb (or 35 lb) bar and lb plates.
- `js/tracking.js`: per tracking type set fields, weight labels ("kg each hand", "kg added", "kg assistance", "kg total"), suggestions, personal-best checks (heavier, more reps, longer, further) and set text.
- Workout mode rows follow the tracking type; timed exercises get a large hold timer (finishing fills and ticks the next set). Swap uses `alternativesFor()` with the old fallback.
- Library page `#library` (Training tab): search, filters, details, history, create/edit/delete own exercises (`state.customExercises`, ids `u_`; deleting keeps `{ deleted: true }` so sync doesn't revive it; renaming keeps the old name in `aka`).
- Progress, records, recap, summary and coach context are type-aware and use the chosen unit. Assisted exercises are judged on reps.
- Known leftover: the same exercise logged under two stored keys (for example `core` and `x_plank`) shows twice on Progress; the Library page merges them.

### Stage 2: detailed muscles and fatigue (done, branch `claude/stage-2-fatigue`)
- `freshness.js` tracks every detailed muscle in `MUSCLE_INFO` separately (`detail` in the result; `PARTS`, `partsFor`). Each body-map group shows its most tired muscle, so old group numbers are unchanged for the same training. Forearms, hips and shins are listed too (not drawn on the outline).
- Set load (`setLoad`): effort tap (Easy 0.7, Hard 1, To failure 1.2; no tap = Hard), weight against your best estimated 1-rep max on that move (0.6 to 1.05), time (sec/40) and distance (m/40). A week well past a muscle's usual full load slows its recovery by up to 30%. Work on a later day than "now" never counts.
- Effort is stored on each done set as `effort: 'easy' | 'hard' | 'fail'`. The tap appears on the workout card once an exercise's sets are ticked, and in the summary.
- Check-in (`readiness.js`): the three main answers are unchanged. `EXTRAS` (hours slept, tiredness, stress, feel ready) are optional, each worst answer adds half a point, and `reasons` lists what pulled it down. Home shows the check-in on rest days too (stored by day, as before).
- Progress recovery: tap a group to see each muscle; tap a muscle for freshness, likely recovery time, a 7-day trend, recent volume (this week and last) and the exercises that worked it (`partWork`, `partVolume` in `stats.js`).
- Coach context lists tired detailed muscles, effort taps and the optional check-in answers.

### Stage 3: smart timetable and fatigue-aware changes (done, branch `claude/stage-3-timetable`)
- `js/timetable.js`: `weekBlocks(state, key)` is now what `blocksFor()` returns: the A/B template, commitments that repeat every N weeks (`every`, `anchor`), minus `history[week].hidden` ids, plus `history[week].extra` one-offs. `windowFor()` gives per-day training hours (`state.dayWindows`, or `history[week].windows` for one week). Block fields added: `flex` (flexible), `before`/`after` (travel or prep minutes, used by `freeGaps`). `planWithFlex()` lets flexible commitments give way only when a week can't fit every session.
- Plain-words changes: `parseAvailability()` reads common phrasings locally (school/work start or finish times, can't train, new commitments with times, free mornings/evenings, sore muscles and tiredness). Anything else goes to `functions/api/timetable.js` (forced tool call, thinking off, same key, model and daily limit as the coach). Every change goes through `validateChange()`, the user sees a preview with the plan diff, and `applyChanges()` runs only on Apply. The box is on My week and beside the coach chat.
- `js/adjust.js`: `proposeChanges()` looks at the next two days using estimated muscle freshness at each session's time, today's check-in and what the user said (`history[week].reports[day]`). It suggests swap, move, rest or lighten, each with the reason and what moves. Accept pins moved sessions or adds the key to `history[week].lighten`; No thanks adds the id to `history[week].dismissed`. Locked sessions (`s.locked`, More menu) and commitments are never moved. Shown on This week, flagged on Home, and listed in the coach context (computed without Strava).
- My week: tap a commitment to edit it (day, times, type, flexible, travel, repeats); one-off changes for this week and next are listed with Undo; "Different hours on some days".

### After launch (live on `main`)
- **Timetable photo:** the "Tell Slotted about a change" box takes up to two photos (one per week when Week A/B is on). The page shrinks them (longest side 2000px, JPEG) and posts them to `functions/api/timetable.js` (`readPhotos`). The AI only **transcribes**: it calls the strict `timetable_photo` tool (`PHOTO_SCHEMA`) with every row of every day (label, start, end, free) and any sport or work. It uses `claude-sonnet-5-5` (`PHOTO_MODEL` overrides it; thinking stays on and the tool can't be forced on that model, so the tool is `auto` and the reply is checked), with one try on the coach's model if that fails. App logic does the rest in `js/timetable.js`: `schoolDay()` takes the first and last real class (free periods at either end and breaks in the middle don't count), `photoPlan()` assigns photos to Week A/B (printed labels win, else photo 1 = A and photo 2 = B, with a swap button), and `photoChanges()` updates existing school instead of doubling it. Preview, then Apply per week (`applyChanges(..., { templates })`). Photos are never stored. **Speed:** the page sends one request per photo, in parallel (`askTimetablePhotos`, 90 s limit each, "Try again" on timeout), and the function gives the stronger model 65 s (effort `medium`, `max_tokens` 8000) then the fallback 25 s, so it always answers before the ~100 s proxy limit (a timeout is a 504 `{error:'timeout'}`). A "Study" row is always free (`PH_FREE`); a roll row like "WG" counts as attendance.
- **Sport effort:** a sport commitment's `intensity` is `easy`, `light` or `hard` (`SPORT_EFFORTS` in `js/timetable.js`; anything else reads as `light`). In `js/scheduler.js`, easy sessions add no leg penalty, and the hardest sport on a day is the one the planner works around.
- **Weights are asked for:** a weighted exercise (`weightNeeded()` in `js/tracking.js`: has a weight box and isn't added/assisted/none) can't be ticked without a weight. With none known (nothing typed, no earlier session, no routine start weight, nothing from an earlier set today), the tick doesn't log; it highlights the box and asks "How heavy was it?". Typing 0 means no weight. Later sets start from the first set's weight. "Tick all as planned" leaves exercises with no known weight unticked and names them. Routine rows have an optional "Start kg" (`startKg`, stored in kg) that pre-fills the first session. Old sets saved without a weight are untouched and get a small note in workout mode.
- **Morning workouts:** `profile.timeOfDay` can be `afternoon`, `morning`, `evening` or `mix` (`timePref()` in `js/scheduler.js`). Mix uses a free afternoon first; when sport or commitments take it, it uses 7 to 9am before school (a 6am start only if nothing else fits; evening ranks above 6am). Saving Settings replans the rest of the week. Default stays `afternoon`.
- **Free mornings:** with `timeOfDay: 'mix'`, a day whose first commitment is school or work and starts late (`morningSlot()`: the free gap before it ends between 9:15am and noon, for example school at 9:40) prefers a session before school even when the afternoon is free (`freeMorning` in `bestSlot()`). A day with nothing on is not a free morning. The coach context also lists each next-week day's free windows (`windowLines()`, from `freeGaps`), and the coach may only suggest times inside them.
- **The coach asks (free mornings):** `proposeMornings()` in `js/adjust.js` finds a session planned after midday on a day with a free morning (`morningSlot()` in `js/scheduler.js`: the gap before the first commitment ends between 9:15am and noon) and asks whether to move it there; Yes uses `applyProposal` (pins it), No adds the id to `history[week].dismissed`. Skipped for done, past, locked, hand-placed, can't-train days and heavy-leg sessions on a hard-sport day; at most 2. `prefQuestion()` in `js/app.js` asks once whether to switch Preferred time to Mix (`profile.morningAsked` is `'yes'` or `'no'`; Settings keeps it). Shown as "The coach asks" on the Coach page and in Suggested changes on This week; the coach context lists them and the instructions say the coach can't apply them. All of it is app logic, never the AI.
- **Coach and next week:** `coachContext()` also sends a "Next week" block (`nextWeekLines()` in `js/app.js`): next week's real commitments from `weekBlocks()` (Week A/B, repeats, one-offs) and the planner's own draft plan around them (saved plan if it exists, otherwise computed with `planWithFlex`, never saved). Wording lives in `commitmentLines()` and `planLines()` in `js/coach.js`; the coach instructions tell it to use that draft and never invent times.
- **Typed changes (accuracy):** `parseAvailability()` only keeps a sentence if its fixed rules account for it. It understands Week A/B (`templates` on a change: `['A']`, `['B']`) and travel minutes (`before`/`after` on `set_times` and added blocks). Anything with unhandled meaning ("except", "every other", two travel numbers, a week with a non-timetable change) goes to the AI instead of being guessed. The AI path (`readSentence()` in `functions/api/timetable.js`) uses `claude-sonnet-5-5` (`TEXT_MODEL`; thinking on, tool `auto`, 40 s, then Haiku 20 s), is told Week A and B separately (`timetableContext()`), and may return `clarify` (a question; nothing is applied). The preview shows which week a change touches and a "Applies to" choice when none was named; the "Done" box has Undo (in memory only).
- **Updates arrive straight away:** `sw.js` serves pages, scripts and styles network first (`cache: 'no-cache'`, cached copy when offline or after 4 s), icons cache first, `/api/` never. When a new worker takes over an open page, a "Slotted has been updated" banner offers Reload (never automatic), and the app checks for updates whenever it comes back into view.
- **Connected calendars (Stage A, read):** Settings → Calendars takes iCal links (Google secret address, iCloud public link, Outlook ICS, school apps). `functions/api/calendar/fetch.js` fetches them (https and public hosts only, redirects re-checked, 10 s, 3 MB, must be `BEGIN:VCALENDAR`, `CALENDAR_DAILY_LIMIT` per visitor in `COACH_LIMITS`); nothing stored server-side. `js/ical.js` parses (TZID/UTC/all-day, weekly/daily/monthly repeats, EXDATE, moved occurrences, cancelled and free events, Windows zone names). `calendarBlocks()` in `js/timetable.js` turns this week's and next week's events into `history[week].cal` (type per calendar or guessed from the name, rules by event name in `state.calendarRules`, School calendars merged into one block a day that replaces the timetable's School that day in `weekBlocks()`). The app reads calendars on open and when it comes back into view (at most every 15 min), replans, and shows "Your calendar changed" with Undo (`calHold` stops the undone result coming back). `state.calendars` holds the links. School timetables: `classLike()` (weekday, starts 7am to 3:30pm, at most 2 hours) and `looksLikeSchool()` (10+ class-like events, 60%+ of timed events) let "Work it out" treat a school feed as a School timetable; only class-like events merge into the day's School block (study/free periods via `CAL_FREE` anywhere in the name, and names containing "cancelled", are skipped), after-school events stay separate; a day needs at least 2 classes to become a School block (a lone event keeps its own name). With calendars connected, My week shows each tab's real week (`viewKey`: the Week A/B tab matching this week is this week, the other is next week; without A/B a This week / Next week toggle) and lists that week's calendar events inside each day next to typed-in commitments, sorted by time and tagged "Calendar" (`calItem()`; tap for `calRuleForm()`). "Start with school" hides when the calendar gives school times. The side card "Calendar sync" explains syncing, has Check now and the ignore list. **Stage B (write):** signed-in users can turn on a private calendar link (`state.calendarFeed.token`, random; New link or Turn off revokes it). Before each upload, `refreshExport()` in `js/app.js` stores `state.calendarExport` (this week's plan and next week's draft from `nextWeekDraft()`, built by `sessionEvents()` in `js/ical.js`). `functions/api/calendar/feed/[user]/[token].js` reads that user's `user_data`, checks the token in constant time, and writes it out with `buildICS()` (UIDs end `@slotted`, so importing the feed back is ignored). `/api/me` now returns the user id for the link. Signed-out users can download the same sessions as a `.ics` file. **Google Calendar write:** Settings → Calendars → Connect Google Calendar (`functions/api/calendar/google/start.js`/`callback.js`, scope `calendar.app.created` only, offline access; encrypted tokens in the `google_calendar` table, which must be created from `schema.sql`). `server/gcal.js` makes a "Slotted" calendar and `syncEvents()` makes it match what the app sends (`/api/calendar/google/sync`): gym sessions (`sessionEvents`) and typed-in commitments (`blockEvents`, not calendar-imported ones) for this week and next, matched by `extendedProperties.private.slottedId`, with "Added by Slotted" in the description so reading calendars skips them. `commit()` schedules an update (4 s debounce, skipped when nothing changed); `/api/me` reports `gcal: { available, connected, needsSetup }`. Disconnect revokes the token; account deletion removes it.
- **Routine import (Bevel and other apps):** Bevel has no public API and Strava can't read sets or templates, so the Routine page has "Import from Bevel or another app": up to 6 screenshots (shrunk with `shrinkImage`, never stored) or pasted text go to `functions/api/routine.js` (strict `routine_copy` tool, `ROUTINE_SCHEMA`; Sonnet 5.5 then Haiku, same limits and timeouts as the photo reader). `routineFromCopy()` in `js/routine-import.js` matches names to the library (`matchExercise`, short forms like DB/BB/RDL), cleans sets/reps, turns weights into `startKg` (lb converted), merges workouts split across screenshots, and flags names not in the library. The preview's **Replace my routine** switches to the user's own routine; Undo (in memory) restores the previous one.
- **Gym sessions in My week:** each day on My week also lists that week's gym sessions (`sessionRows()` in `js/scheduler.js`, `gymItem()` in `js/app.js`): this week's saved plan (Done tag, tap opens the workout) or, on the other week tab, next week's draft from `nextWeekDraft()` (Draft tag, never saved; it becomes the plan on Monday). This week ends with a "Next week" draft card (`nextWeekCard()`). The coach instructions say where sessions appear and not to point to screens that aren't described.
- Sign in with Google, D1, the coach limit (`COACH_LIMITS` KV) and PNG app icons (`icons/`) are set up on the live site. Strava is not switched on (needs a Strava subscription to create an API app).
